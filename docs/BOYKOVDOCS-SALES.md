# Продажи инструкций BoykovDocs

В «Клиенты BoykovDocs → Продажи инструкций» показываются покупки PDF и Word: количество, сумма, покупатели, уникальные инструкции, динамика, популярные инструкции и история конкретного покупателя. Периоды: сегодня, 7/30/90 дней, всё время. Дни считаются по Москве; сегодняшний день включён. Есть поиск по имени, почте, телефону и ID, фильтр формата, сортировка и постраничные списки. Экран обновляется каждые 30 секунд, когда открыт.

## Что считается продажей

Источник соответствует существующей админке BoykovDocs: `purchases` из `/app/data/wallets.json`, версия 1. Одна запись — одна покупка доступа к формату инструкции; PDF и Word одной инструкции считаются двумя покупками, а уникальная инструкция — одной. Повторное скачивание ничего не добавляет. Сумма берётся из сохранённого `amountMinor` в копейках, а не из текущей цены. Это сумма покупок доступа, не бухгалтерский отчёт об оплатах, возвратах или чеках. Пополнения баланса, платежи, фискальные события и события скачивания сюда не попадают. Отдельные заказы публичной платной генерации, не входящие в этот источник админки, также не включены.

Загружается **вся доступная история покупок**, чтобы «Всё время» соответствовало источнику. Покупатели хранятся отдельно: старые регистрации и компании в клиентский список не импортируются. Пользователь определяется по неизменному ID BoykovDocs, а не по совпадению почты или имени. При наличии действующей CRM-карточки можно открыть её из истории покупок. Покупка не восстанавливает карточку из корзины. Покупки без записи пользователя в источнике остаются связаны с исходным ID и учитываются в статистике.

## Установка

1. Применить архивный патч в локальном корне проекта PowerShell-командой из архива. Установщик делает резервную копию изменяемых файлов внутри `.git/boykov-patch-backups`, проверяет применимость, запускает `npm run check`. Повторный запуск проверяет уже установленный патч и снова запускает проверки. Коммитов и push не делает. База патча: `93fbf73` или совместимая версия.
2. Закоммитить и отправить изменения обычным способом.
3. **На VPS Boykov Services**:

```bash
cd /opt/boykov-services
git pull --ff-only
bash scripts/deploy-docs-customers.sh
```

Скрипт сохраняет согласованную резервную копию SQLite через `VACUUM INTO`, проверяет её, сохраняет предыдущий образ и команду отката; пересобирает только `app`, проверяет миграции и закрытость API/вебхуков. Ожидаемые результаты: `DOCS_SALES_MODULE=OK`, `DOCS_SALES_AUTH=OK`, `DOCS_CUSTOMERS_DEPLOY=OK`.

4. **На VPS BoykovDocs (`cv8367491`)**, где уже установлен коннектор клиентов:

```bash
cd /opt/boykov-services-connector
git pull --ff-only
bash scripts/install-docs-sales.sh
```

Существующий приватный ключ из `/opt/boykovdocs-customers-delivery/config.json` используется автоматически. Копировать ключ в чат или вводить его заново не нужно. Сначала проверяется новый вебхук. Затем устанавливается отдельный контейнер `boykovdocs-sales-delivery-delivery-1` с собственной SQLite-очередью; ожидается `DOCS_SALES_CONNECTION=OK`. Первичная загрузка идёт порциями по 50 событий, поэтому для большой истории некоторое время будет статус «Загружаем историю продаж». Новые события получают приоритет, старая очередь также продвигается.

Новый процесс только читает каталог `/app/data` через read-only mount. Код и корневая файловая система контейнера также read-only. Он не загружает код приложения BoykovDocs, не меняет кошельки, баланс, пользователей, документы, оплаты, чеки и письма; сайт и работающий коннектор клиентов не перезапускаются. Передаваемые поля ограничены ID покупки/пользователя/инструкции, названием, форматом, суммой, датой и контактами покупателя. Пароли, токены пользователей, содержимое инструкций и фискальные данные исключены.

## Проверка и восстановление

```bash
docker compose -f /opt/boykovdocs-sales-delivery/compose.json ps
docker compose -f /opt/boykovdocs-sales-delivery/compose.json logs --tail 20 delivery
```

Логи содержат только счётчики и коды состояния. `SOURCE_PURCHASES` — число покупок в источнике; `PENDING` — очередь, которая должна уменьшаться до нуля; `REJECTED=0` — нет отвергнутых событий. Ключи и контакты не выводятся. Отдельный cron не требуется.

При первом подключении до получения данных сервис показывает «Ожидает первого запуска», а не подтверждённый ноль продаж. Полнота сверяется по числу покупок в источнике и сервисе. Отсутствие heartbeat более трёх минут, повреждённый источник, удаление записей из источника, невалидное подтверждение и конфликты выводят предупреждение. Сохранённая история при сбое остаётся доступна. При сбое сети события остаются в очереди с повторными попытками; положительное подтверждение проверяется по ID события, покупки и пользователя. Повторная доставка не удваивает продажи. Изменение владельца, цены или реквизитов уже записанной покупки отвергается, а не перезаписывает историю.

Резервная копия конфигурации коннектора выводится как `BACKUP=...`; при ошибке установки восстанавливается предыдущая конфигурация, если она существовала. Очередь не удаляется. Центральный деплой выводит каталог с `rollback-app.sh`, предыдущим образом и JSON-путём резервной базы. Откат приложения выполняется через этот скрипт; базу не следует заменять без отдельного решения, поскольку в неё уже могли поступить новые данные.

При ротации общего ключа BoykovDocs нужно обновить оба коннектора: клиентов и продаж. После обновления конфигурации клиентов повторно запустить `install-docs-sales.sh`. Очередь сохраняется.

## Проверки разработки

`npm run check`: сборка TypeScript/Vite и полный набор Node-тестов. `tests/docs-sales.test.js` проверяет авторизацию, историю без импорта старых CRM-карточек, связь по ID при одинаковой почте, суммы/форматы/границы дня Москвы, пагинацию, дедупликацию, неизменность покупки, корзину, read-only сбор, фильтрацию полей, очередь, неверный ACK, повреждение/уменьшение источника. Скрипты проверяются `bash -n`; фактические Docker-монтажи и доступ к производственному источнику проверяет установка на VPS.
