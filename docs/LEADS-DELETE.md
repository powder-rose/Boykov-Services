# Удаление и восстановление заявок

В карточке есть кнопка «Удалить заявку». В списке можно отметить отдельные
строки или выбрать текущую страницу целиком и нажать «Удалить выбранные».
Выбор ограничен текущей страницей: максимум 50 записей за операцию.
При изменении фильтра или страницы выбор сбрасывается. Перед действием
показывается подтверждение с количеством выбранных заявок.

Удаление переносит заявки в корзину. Они исчезают из входящих, счётчиков сайтов
и новых заявок на главной. Кнопка «Корзина» открывает отдельный список с поиском,
фильтром сайта и статуса. Данные формы, статус, комментарий и история сохраняются.
Можно восстановить одну заявку из карточки или несколько выбранных из списка.
Восстановленные заявки возвращаются с прежним статусом. Автоматической очистки
корзины и безвозвратного удаления в этой версии нет.

Несохранённый черновик в карточке необходимо сначала сохранить, чтобы удалить
заявку. Удалённые карточки доступны для просмотра; редактирование статуса и
комментария включается после восстановления. История отмечает перенос в
корзину и восстановление.

Для удаления и восстановления нужна действующая сессия сотрудника и штатная
защита от межсайтовых запросов. Ключ приёма заявок не даёт права удаления.
Доступ остаётся общим, как в остальных разделах сервиса.

## Повторы, конкурирующие изменения и сбои

Уникальность `site_id/event_id` и исходный хеш остаются в базе. Все четыре
источника, включая Tilda, получают подтверждение повторной доставки исходной
заявки, но удалённая заявка не восстанавливается автоматически. Новое обращение
с другим номером сохраняется обычным образом, даже если телефон совпадает.

POST `/api/leads/trash` принимает `{requestId, action, leads: [{id, version}]}`.
`action` — `delete` или `restore`. Группа из 1–50 различных записей меняется одной
транзакцией `BEGIN IMMEDIATE` с проверкой версий. Статус или комментарий,
сохранённые другим сотрудником, делают старый выбор недействительным: вся
операция откатывается, интерфейс предлагает обновить список и выбрать заново.
После успешного COMMIT возвращается подтверждение. Ошибка записи или истории
не оставляет частично выполненную группу.

`requestId` сохраняется в `sales_actions` с хешем состава операции. При потере
ответа интерфейс повторяет тот же запрос. Повтор не создаёт новую запись истории
и не удаляет заново заявку, которую после первой операции уже восстановили.

Миграция добавляет `sales_leads.deleted_at` и `sales_history.action`, сохраняя
существующие заявки, ключи и статусы. API списка по умолчанию показывает входящие;
`?view=trash` показывает корзину. Старые клиенты не получают удалённые записи.

## Обновление VPS

После локальной установки, успешной проверки и push:

```bash
umask 022
cd /opt/boykov-services
git pull --ff-only && bash scripts/deploy-leads-delete.sh
```

Скрипт сохраняет онлайн-копию SQLite и предыдущий образ приложения. Собирается
и перезапускается только `app`. Проверяются healthcheck, целостность базы и поля
миграции. Ожидаемый результат: `LEADS_DELETE_DEPLOY=OK`, путь `BACKUP`.

В каталоге BACKUP находится `rollback-app.sh`, возвращающий старый образ без
восстановления старой базы поверх новых поступлений. Старый код не учитывает
корзину: после такого отката ранее удалённые записи снова отображаются во
входящих, данные сохраняются. Подключения сайтов и ключи менять не требуется.
