# Заявки с сайтов

## Работа отдела продаж

Раздел открывается через пункт «Заявки» или `/#leads`. На главной и в меню
видно количество новых обращений. В разделе есть выбор сайта, поиск по имени,
телефону, почте и данным формы, фильтр статуса и три порядка сортировки.
Список разбит на страницы по 50 записей и обновляется каждые 15 секунд.
Время отображается по Москве, с годом для ранее сохранённых обращений.

Статусы: «Новая», «В работе», «Обработана». Последний статус означает, что
менеджер обработал обращение; результат общения записывается в комментарий.
Карточка сохраняет исходные данные и историю изменений. Два сотрудника не
могут незаметно перезаписать одну версию. Потерянное подтверждение сохранения
можно повторить с тем же идентификатором операции. Повторная доставка с сайта
не меняет комментарии или статус менеджеров.

Текущий доступ общий, как в остальных разделах Boykov Services. История
показывает время и содержание изменений, без выдуманной персональной
атрибуции сотрудника. Заявку можно удалить в корзину из карточки или выбрать
несколько заявок на текущей странице. Корзина позволяет восстановить данные
с прежними статусами и комментариями. Повторная доставка не возвращает
удалённые заявки во входящие. Подробности: [удаление заявок](LEADS-DELETE.md).

## Что устанавливает патч

Патч меняет Boykov Services и добавляет исходники коннекторов. Он не подключает
формы удалённых сайтов автоматически и не меняет их сервера при локальной
установке. Четыре сайта добавлены заранее, включая boykovgroup.ru на Tilda. До настройки источник показывает
«Не подключён». Создание ключа само по себе не подтверждает подключение.

Ключ создаётся в карточке подключения нужного сайта и показывается один раз.
В базе хранится только SHA-256 ключа. Создавайте рабочие ключи на боевом
Boykov Services после его обновления. Ключ находится только на сервере сайта в закрытом конфигурационном файле
или в настройках приёмщика Tilda. Для каждого сайта используется свой ключ.
Новый ключ сразу заменяет предыдущий и требует обновления агента.

Добавление ещё одного сайта доступно через «Добавить сайт»: название, домен,
новый отдельный ключ. Домен вводится без протокола и пути. Выберите способ подключения: серверный агент или Webhook Tilda.
Для Tilda используйте [отдельную инструкцию](TILDA.md).

## Приём и контроль доставки

`POST /hooks/leads/{siteId}` принимает JSON с заголовком
`Authorization: Bearer KEY`. В браузер публичного сайта этот ключ не передаётся.
Маршрут работает отдельно от сессионной авторизации сотрудников.

```json
{
  "eventId": "unique-source-record-id",
  "createdAt": "2026-11-18T10:00:00.000Z",
  "name": "Имя клиента",
  "phone": "+7 999 000-00-00",
  "email": "client@example.ru",
  "service": "Название услуги",
  "message": "Сообщение клиента",
  "pageUrl": "https://example.ru/service/",
  "form": "Форма консультации",
  "fields": [{ "label": "Объект", "value": "Описание объекта" }]
}
```

Обязательны стабильный `eventId` и исходная дата с часовым поясом. Контактные
поля могут отсутствовать у старых записей: такое обращение сохраняется для
ручного разбора. Дополнительные поля имеют вид `label/value`, максимум 100.
Тело запроса ограничено 128 КБ; превышение и ошибки формата возвращают отказ,
отправитель сохраняет запись в очереди. Строки не обрезаются молча.

Подтверждение — только HTTP 200/201 с JSON
`{ok:true, siteId, eventId, id}`. `id` — номер сохранённой записи в центре.
Сайт проверяет совпадение `siteId` и `eventId`. Ответ 202, HTML, редирект,
ошибка разбора ответа и тайм-аут подтверждением не являются.

Запись и начальная история сохраняются одной транзакцией SQLite с
`synchronous=FULL`. После COMMIT отправляется подтверждение. Пара
`siteId/eventId` уникальна. Совпадающий повтор возвращает исходный номер;
другое содержимое с тем же номером возвращает 409 и ничего не перезаписывает.
Обращения с одинаковым телефоном и разными номерами не склеиваются: это могут
быть разные услуги и продажи.

Агент передаёт `POST /hooks/leads/{siteId}/heartbeat`:
`{pending, rejected, scanOk, oldestPendingAt}`. Отсутствие сигнала более двух
минут, ошибка чтения источника, отклонённые записи или очередь старше пяти
минут отражаются в интерфейсе. Эти показатели описывают доставку, а не
доступность каждой публичной страницы сайта. Контрольная отправка через
реальные формы обязательна при подключении и после изменения самих форм.

## Порядок подключения

1. Установить патч локально и выполнить проверки. Обновить GitHub и VPS
   Boykov Services обычным порядком с резервной копией существующего тома.
2. В боевом разделе создать отдельный ключ каждого сайта.
3. Установить сохранение копий и отправителя на соответствующем сайте.
4. Проверить сигнал доставки, отправить контрольное обращение из каждой
   разновидности формы и сопоставить его номер с исходной записью.
5. Проверить повторную доставку и обработку карточки. После остановки
   отправителя источник должен показать отсутствие сигнала, после запуска
   очередь должна доставиться с сохранением статусов менеджеров.

Источник считается рабочим после этих проверок. Почта и существующие CRM
продолжают работать своим обычным способом. Центр не извлекает заявки из
Яндекс Метрики: событие аналитики не является сохранённым обращением.

### Паспорт доступности

На сервере `/opt/accessibility-passport` используется Node.js 24 и SQLite.
Сначала установите `integrations/leads/accessibility-outbox.mjs` в контейнер
приложения и запустите его, передав **существующий** путь `DATABASE_PATH` и
новое имя резервной копии в постоянном томе:

```bash
node /tmp/accessibility-outbox.mjs /app/data/site.sqlite /app/data/backups/pre-sales-UNIQUE.sqlite
```

Скрипт проверяет схему и делает `VACUUM INTO` до изменений. Триггер копирует
каждую новую заявку в `boykov_lead_outbox` в той же транзакции. Существующие
заявки также копируются. Удаление из старой админки не удаляет эту копию.
`user_version` и прежняя схема приложения сохраняются.

После этого запускается агент с форматом `accessibility-sqlite`. Он читает
только таблицу копий и проверяет наличие триггера. Доступ к исходному тому
даётся только на чтение. Вложения показываются в центре как метаданные;
сами файлы остаются в исходной админке сайта.

### Паспорт безопасности

В `integrations/leads/patches/security-passport.patch` находится отдельный
патч для репозитория Security-Passport, подготовленный относительно коммита
`e58e59211aaec19881328db41bd780f3f38d7056`. Его нужно применить в том
репозитории с `git apply --check`, проверить и включить в обычную публикацию.

На сервере задаётся `BOYKOV_HUB_OUTBOX` — абсолютный путь к отдельному
постоянному журналу вне каталогов релизов. Перед ответом публичной форме
запись добавляется туда с синхронизацией файла и каталога. Проблема записи
не превращается в успешную отправку формы. Удаление из прежней админки
не затрагивает журнал доставки.

Сначала опубликуйте обработчик с этой настройкой, затем дополните журнал
ранее сохранёнными обращениями:

```bash
node backfill-security-outbox.mjs /existing/data/leads.jsonl /persistent/hub-outbox.jsonl
```

Пути должны соответствовать действующим `LEADS_FILE` и `BOYKOV_HUB_OUTBOX`.
Скрипт дописывает журнал, не заменяет его. Повторы исходного номера безопасны.
Формат агента — `security-jsonl`, источник — именно журнал доставки.
При очередных релизах настройка и патч обработчика должны сохраняться.

### Запуск агента Node.js

Код `agent.mjs`, `compose.agent.yaml` и `agent.env.example` копируется в
отдельный каталог на сервере исходного сайта. Пример конфигурации копируется
в `.env.agent` с правами 600 и заполняется закрытым ключом. `SOURCE_DIRECTORY`
указывает на постоянный каталог данных; `LEADS_SOURCE_FILE` — соответствующий
путь внутри `/source`. Для каждого сайта выбирайте отдельный Compose-проект:

```bash
docker compose --env-file .env.agent -p boykov-leads-accessibility -f compose.agent.yaml up -d
```

Для второго сайта имя проекта — `boykov-leads-security`. Агент работает
каждые 15 секунд. Его собственная очередь находится в отдельном постоянном
томе. Она проверяет подтверждения, повторяет отправку без лимита попыток и
использует задержку до 15 минут после повторных сбоев. Очередь привязана к
источнику и адресу центра, чтобы случайная смена конфигурации не перенесла
чужие обращения в другой сайт. Смена ключа разрешена без сброса очереди.

### NWD Electricity на Beget

Проверен пользовательский обработчик
`/home/i/infonwt4/nwdelectricity.ru/public_html/custom/energo/modules/feedback/feedback.action.php`
с транзакцией `nwd_feedback_request` и помощником `nwdFeedbackLead()`.
Установка выполняется через тот PHP 7+, которым работает существующая панель;
показанный по умолчанию CLI `php` 5.6 для панели не подходит. Ранее выбранный
путь к PHP записан в `/home/i/infonwt4/.nwd-production/forms-xEg9WQjP/php`.

Четыре файла из `integrations/leads/nwd` копируются **вне public_html**, например
в `/home/i/infonwt4/.nwd-production/boykov-leads/code`. После этого:

```bash
nwd_php=$(cat /home/i/infonwt4/.nwd-production/forms-xEg9WQjP/php)
nwd_root=/home/i/infonwt4/nwdelectricity.ru/public_html
nwd_private=/home/i/infonwt4/.nwd-production/boykov-leads
"$nwd_php" "$nwd_private/code/install.php" "$nwd_root" "$nwd_private"
```

Установщик проверяет InnoDB, версию обработчика и синтаксис, сохраняет его
копию и добавляет вызов очереди перед COMMIT. В `boykov_lead_outbox` создаётся
снимок данных вместе с заявкой и почтовой очередью. Существующие обращения
переносятся без изменения оригиналов. Доставка выполняется отдельным PHP
процессом; Node.js на Beget не нужен. Настройте закрытый ключ через stdin:

```bash
IFS= read -r -s -p 'Ключ сайта NWD из раздела Заявки: ' nwd_key
printf '\n'
printf '%s\n' "$nwd_key" | "$nwd_php" "$nwd_private/code/configure.php" "$nwd_root" "$nwd_private"
unset nwd_key
"$nwd_php" "$nwd_private/code/run.php" "$nwd_private/config.php"
```

В панели хостинга добавьте выполнение последней команды каждую минуту,
используя **фактический** путь к выбранному PHP. Конфигурация и блокировка
хранятся вне web-root. Отправитель проверяет TLS и подтверждение по номеру
записи, оставляет неподтверждённые записи в MySQL и повторяет попытки.

## Эксплуатация и восстановление

Все скопированные исторические обращения получают статус «Новая» в центре;
старые статусы сторонних админок автоматически не интерпретируются.
Исходные сведения неизменяемы, обработка отдела продаж хранится отдельно.
Копии и очереди не очищаются автоматически в этой версии.

Резервировать нужно постоянный том Boykov Services, исходные базы и журналы,
тома агентов и закрытые конфигурации. Копию SQLite делают согласованно —
через его механизм резервирования или с остановленными писателями, а не
копированием одного файла активной WAL-базы. При откате кода тома сохраняются.
`docker compose down -v` удаляет тома и для штатного обновления не применяется.

Повреждённые записи и несовпадающее содержимое номера остаются в исходнике
и/или локальном журнале отказов агента; ошибка отображается в состоянии сайта.
Исправлять их нужно с сохранением оригинала, затем повторить доставку.
Восстановление после сбоя не должно начинаться с очистки очереди.

Надёжная доставка опирается на постоянные хранилища, включённые отправители,
проверку реальных форм и резервные копии. Патч проверяет повторы, сбои записи,
потерю подтверждения, перезапуск и конкурентную обработку; проверка на живых
серверах выполняется при подключении. Проверка интерфейса в рабочем браузере
и контрольная отправка из реальных форм входят в приёмку обновления.
