# BoykovDocs — продажи генераций и пополнения

В «Клиенты BoykovDocs» добавлены отдельные вкладки «Генерации» и «Пополнения». Используются существующие палитра, карточки показателей, точки заголовков, контакты и диалоги. Доступ такой же, как к продажам инструкций: авторизованное рабочее пространство. Старые вкладки, карточки компаний и отметки звонков сохраняются.

## Работа с отчётами

Периоды: всё время, сегодня, 7/30/90 календарных дней по Москве. Итоги относятся ко всему выбранному периоду; поиск фильтрует список пользователей. Поиск — имя, телефон, email или ID. Сортировка — последняя операция, количество, сумма. Числа сохраняют точность в копейках, суммы выводятся в рублях.

В строке пользователя видны число оплаченных заказов/зачислений, сумма, возвраты и последняя операция. «История» открывает карточку этого пользователя. В генерациях инструкции сгруппированы по названию с количеством покупок и суммой; ниже показан каждый заказ, время, статус и дата готовности. В пополнениях — отдельные зачисления и возвраты. Списки и группы имеют независимую пагинацию по 25, без скрытого ограничения общего числа операций.

Идентичность — ID BoykovDocs, email не объединяет разных пользователей. Для существующей активной CRM-карточки есть переход «Карточка клиента». Покупки исторических пользователей не создают старые CRM-профили и компании. Удаление карточки клиента не стирает финансовую историю и не восстанавливает её автоматически.

Старые заказы без ownerUserId отображаются как гостевые, с email из заказа при наличии. Каждый такой заказ остаётся отдельным; их число вынесено в пояснение и не выдаётся за уникальных зарегистрированных покупателей.

## Правила расчёта

- Генерация — один оплаченный заказ publicGenerationOrders. Повторные заказы на одну профессию учитываются отдельно. Повторные скачивания и попытки генерации не увеличивают продажи. Считается фактическая оплаченная сумма, включая скидки.
- Учитываются подтверждённые live/legacy оплаты в статусах paid, moderating, generating, generated, manual_review, refunding, refund_pending, refunded, как в текущем отчёте продаж BoykovDocs. Нужны transactionId и paidAt. TestMode, test_paid, неоплаченные и заказы с PAYMENT_MISMATCH/DUPLICATE_TRANSACTION исключаются.
- Пополнения берутся из wallets.json.payments. Созданное намерение topups без подтверждённого платежа не считается поступлением. Возвраты из refunds проверяются по paymentId, orderId, userId и общей сумме; до появления соответствующего Pay возврат не участвует в состоянии кошелька. Поздний Pay после ранее записанного Refund поддерживается.
- Покупки инструкций со счёта остаются в «Продажах инструкций». Пополнение и покупка не складываются в единую выручку.
- Возврат учитывается датой возврата, даже если покупка была раньше выбранного периода. «После возвратов за период» — поступления/покупки минус возвраты в этом периоде; это не текущий остаток кошелька. Валовая сумма оплаченных заказов сохраняется, возвраты показаны отдельно.

## Доставка и данные

Новые API: GET /api/docs-commerce/report и /api/docs-commerce/buyers/:id с параметрами kind=generations|topups, period, q, sort, page; в истории дополнительно groupsPage. API закрыты существующим входом, ответы no-store.

POST /hooks/docs-customers/commerce, /heartbeat и /handshake используют существующий приватный ключ клиентов BoykovDocs. Протокол 1, scope generations-and-topups. При изменении ключа клиентского подключения требуется обновить конфигурации всех использующих его коннекторов.

Таблицы SQLite docs_commerce_buyers/operations/receipts/connection добавляются автоматически. Суммы и принадлежность подтверждённых платежей неизменяемы. Ключ записи — kind+id. Для генераций более новая updatedAt обновляет статус и результат; запоздавшая версия его не перезаписывает. Одинаковый eventId с другими данными возвращает 409, повторная доставка не удваивает запись. Сопоставление возвратов выполняется транзакционно, включая доставку возврата раньше родительского платежа.

Коннектор integrations/docs-customers/commerce-agent.mjs работает отдельно от приложения BoykovDocs и использует проверенный транспорт sales-agent.mjs. Каталоги источника монтируются только для чтения:

- /app/data контейнера boykovdocs-api — users.json и wallets.json;
- /app/src/data — publicGenerationOrders.

Контакты и минимальные поля оплаченного заказа проходят явный список разрешённых полей. Документы, accessToken, пароли, фискальные контексты, персональные согласия и платёжные реквизиты не отправляются. Приложение BoykovDocs не импортируется и не вызывается.

Собственная SQLite-очередь с WAL, synchronous=FULL, постоянным состоянием, проверкой ACK и повторами сохраняет события при недоступности сети и потерянных ответах. Обновления проверяются раз в 30 секунд. Ошибка чтения источника не выдаётся за пустой успешный отчёт. Уменьшение числа исходных операций, расхождение количества, отказ доставки и устаревшее подтверждение видны в статусе. История доставки не очищается при переустановке.

## Установка

После применения патча PowerShell-установщиком в корне проекта, npm run check, коммита и push:

На VPS Boykov Services:

```bash
cd /opt/boykov-services
git pull --ff-only
bash scripts/deploy-docs-commerce.sh
```

Ожидается DOCS_COMMERCE_DEPLOY=OK. Скрипт сохраняет согласованный снимок SQLite и предыдущий Docker-образ, обновляет app, проверяет миграцию, health и авторизацию. Путь BACKUP содержит rollback-app.sh; всю БД автоматически не заменять, поскольку после снимка могли поступить новые данные.

Затем на VPS BoykovDocs (где работает boykovdocs-api):

```bash
cd /opt/boykov-services-connector
git pull --ff-only
bash scripts/install-docs-commerce.sh
```

Ожидается DOCS_COMMERCE_CONNECTION=OK. Переиспользуется закрытый ключ /opt/boykovdocs-customers-delivery/config.json, вводить его заново не нужно. Перед запуском проверяются handshake и реальные пути томов. Отдельный контейнер boykovdocs-commerce-delivery-delivery-1 и его состояние находятся в /opt/boykovdocs-commerce-delivery. В начале передаётся история подтверждённых операций, затем изменения. Существующие сайт, доставка клиентов и продажи инструкций не перезапускаются. Дополнительный cron не нужен.

Проверка доставки:

```bash
docker compose -f /opt/boykovdocs-commerce-delivery/compose.json ps
docker compose -f /opt/boykovdocs-commerce-delivery/compose.json logs --tail 15 delivery
```

Установщик сохраняет предыдущие конфигурации и согласованную копию очереди, при ошибке пытается вернуть предыдущий контейнер. Не копируйте старую очередь поверх новой автоматически: в ней могут быть более новые подтверждения. Если пути томов отличаются, скрипт завершится до подключения с DOCS_COMMERCE_GENERATION_SOURCE_NOT_FOUND или DOCS_COMMERCE_SOURCE_DATA_NOT_FOUND; для уточнения достаточно списка mount-путей контейнера, секреты не нужны.
